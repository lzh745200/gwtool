# Domain Docs

工程技能在探索本仓库时，应如何消费这里的领域文档。

## 本仓库的布局结论：single-context

**本仓库是 single-context**：一个仓库共用**一份根目录 `GLOSSARY.md`**，
架构决策放在根目录的 `docs/adr/`。

因此**不要**创建 `GLOSSARY-MAP.md`，也**不要**在子项目里各放一份 `GLOSSARY.md`。
只有当领域词条或架构决策真正被写下时，才惰性创建对应文件；本次初始化不建空壳。
（初始化时已全仓核查：不存在需要迁移的旧名领域文档，故本次没有任何改名动作。）

```
/
├── GLOSSARY.md            ← 全仓库共用的领域词汇表（尚未创建，写第一个词条时建）
├── docs/
│   ├── adr/               ← 架构决策记录（尚未创建，写第一条决策时建）
│   │   ├── 0001-xxx.md
│   │   └── 0002-xxx.md
│   └── agents/            ← 技能套件的 per-repo 配置（本次产出）
└── gwtool/                ← 主包：core / db / ui
```

## 探索前先读这些

- 根目录的 **`GLOSSARY.md`**：领域概念的权威定义。
- **`docs/adr/`**：读与你要改动的区域相关的 ADR。

如果这些文件还不存在，**静默继续**即可 —— 不要提示"缺文件"，也不要主动建议先建。
`/domain-modeling` 技能（经 `/grill-with-docs`、`/improve-codebase-architecture` 抵达）
会在词汇或决策真正被解决时才惰性创建它们。

## 使用词汇表里的说法

当你的产出要提到某个领域概念（issue 标题、重构提案、假设、测试名）时，
用 `GLOSSARY.md` 里定义的那个词，不要漂移到词汇表明确回避的同义词。

如果需要的概念不在词汇表里，这本身是个信号：要么你在发明项目不用的说法（重新考虑），
要么确实存在缺口（记下来交给 `/domain-modeling`）。

## 发现与 ADR 冲突时要显式指出

如果你的产出与既有 ADR 矛盾，明确说出来，不要悄悄覆盖：

> _与 ADR-0007（事件溯源订单）冲突，但值得重开，因为……_
