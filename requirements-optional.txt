# 公文汇编助手 —— 【可选】精度增强包依赖（不并入主 requirements.txt）
#
# ⚠️ 为什么单独一个文件
# ---------------------------------------------------------------------------
# 主 requirements.txt 是 CI 双平台（windows-latest x64 + ubuntu-24.04-arm）
# 构建与打包装箱单的唯一来源。把 onnxruntime 塞进去会带来两个直接风险：
#   1) 麒麟 CI 在 Debian 11 容器内用 **Python 3.9** 构建（为守住 glibc 2.31
#      底线不能升级容器），而 onnxruntime 新版本要求 Python >= 3.11；
#   2) 一旦装不上或版本解错，打包会以「同源码、不同日期产物行为不同」的方式
#      失败——这正是 v1.2.1「启用口令锁即崩」事故的成因。
# 因此**默认安装不包含**本文件，纠错功能在无 onnxruntime 时照常工作
# （走三级流水线，见 gwtool/core/csc_neural.py 的硬约束说明）。
#
# 何时安装
# ---------------------------------------------------------------------------
# 只有在准备启用「L4 神经精排」时，才需要在一台有网的机器上执行：
#     pip install -r requirements-optional.txt
# 然后**离线**取得一个精度增强包（.zip），在软件「设置 → 文字纠错」里导入。
#
# 版本必须分档（与主 requirements 同一套纪律：不写浮动版本）
# ---------------------------------------------------------------------------
# · Python >= 3.11：可用 1.19 ~ 1.27 一档；
# · Python 3.9（麒麟 CI 容器）：只能停在 1.17 一档——更高版本已放弃 3.9；
# · aarch64（麒麟 V10）：**已实测确认可用，无需再注释掉**。见下方"aarch64 实测结论"。
#
# aarch64 实测结论（2026-09-15 核对 PyPI 元数据，勿凭印象推翻）
# ---------------------------------------------------------------------------
# 曾长期把 aarch64 那行注释掉，理由是"上游轮子可用性不稳、须上机核对 glibc"。
# 实测核对后该顾虑**不成立**，故现已启用：
#   · onnxruntime 1.17.3 提供 aarch64 轮子，标签为
#     `manylinux_2_27_aarch64.manylinux_2_28_aarch64`，
#     即有 cp38/cp39/cp310/cp311/cp312 六个版本，**含 cp39**（麒麟 CI 的
#     Debian 11 容器正是 Python 3.9，版本恰好对得上）；
#   · glibc 基线 = 2.27/2.28 **低于**本项目 ARM64 底线 2.31 → 在麒麟 V10 上
#     不会出现 "version `GLIBC_2.xx' not found"。这是它可用的关键依据。
#   · tokenizers 0.15.2 同样有 aarch64 轮子（`manylinux_2_17_aarch64`，
#     glibc 2.17，含 cp39），L5 的分词器在 aarch64 上同样可用。
#   · numpy 传递依赖：onnxruntime 要求 `numpy>=1.21.6`，**且声明里没有上界**。
#     ⚠ onnxruntime 1.17.3 是用 **NumPy 1.x** 编译的，ABI 与之绑定：装到
#     numpy 2.x 后导入即报
#       `AttributeError: _ARRAY_API not found`
#       （附 "A module that was compiled using NumPy 1.x cannot be run in
#        NumPy 2.x as it may crash."），L4 直接不可用。
#     ⚠ **不能指望"py39 会自然落到 1.x"**——numpy 2.0.2 是有 cp39 轮子的。
#     2026-09-16 CI 实测正是装上了 2.0.2 才失败（tokenizers/numpy 就绪、
#     onnxruntime 导入异常）。因此下面**显式钉上界 numpy<2**。
#     旧注释曾写"numpy 2.x 已放弃 3.9，3.9 档会被解析到 1.x"——该说法已被
#     实测推翻，勿再依此删掉约束。
# 结论：L4 与 L5 在 Windows x64、Linux x86_64、麒麟 V10 ARM64 三个平台上
#       依赖齐备；真正决定"能否启用"的只剩**是否导入增强包**这一件事。
#
# 注意：onnxruntime 会引入 numpy 依赖；本项目其余代码不需要 numpy。

# ---- Windows x64 / Linux x86_64（Python >= 3.11）：1.19 ~ 1.27 一档 ----
onnxruntime==1.27.0 ; python_version >= '3.11'

# ---- Python 3.9（麒麟 CI 容器一档；支持 3.9 的最后一档） ----
# 这一档同时覆盖 **aarch64**：1.17.3 的 cp39 aarch64 轮子已实测存在且
# glibc 基线（2.27/2.28）低于本机底线 2.31，故无需为架构单独分叉版本。
# 不要再加 `platform_machine == 'aarch64'` 的单独行——它会把 aarch64 拉到
# 与 x86_64 不同的版本上，制造"同源码不同行为"的分叉（v1.2.1 事故模式）。
onnxruntime==1.17.3 ; python_version < '3.11'

# ---- L5 语法纠错包（Seq2Seq / BART 一类）额外需要的分词器 ----
# 只装 L4（拼写）不需要它；不装本包时 L5 自动静默，纠错行为不变。
#
# 为什么选 tokenizers 而不是自研分词器：
#   Seq2Seq 模型对分词极度敏感（`##` 续接、[CLS]/[SEP] 包裹、全角/半角归属），
#   自研实现与预训练时用的 WordPiece 只要有一处偏差，精度就会明显掉。
#   tokenizers 是 HuggingFace 官方的 **Rust** 实现，约 5–8 MB，**不含 torch**，
#   与本项目"不引入 torch"的红线不冲突。
# aarch64 已实测：0.15.2 提供 cp39 `manylinux_2_17_aarch64` 轮子（glibc 2.17
#   基线，低于本项目 ARM64 底线 2.31），麒麟 V10 可直接安装，无需额外分叉。
#
# 版本分档：新版已放弃 3.9，故与 onnxruntime 同样分两档。
tokenizers==0.22.0 ; python_version >= '3.11'
tokenizers==0.15.2 ; python_version < '3.11'

# onnxruntime 1.17.3 的 ABI 绑定 NumPy 1.x：必须显式钉上界，
# 否则 pip 会装 numpy 2.x（它有 cp39 轮子）导致导入失败。
numpy<2 ; python_version < '3.11'
