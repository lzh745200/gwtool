# v1.20.1 修复记录（第十轮全面排查）

> 基线 v1.20.0。这一版不加功能，只把排查出的缺陷修掉。八项里四项会造成用户
> 可见后果，另外四项是一致性与健壮性问题。每条都先复现、再修、最后固化成护栏用例
> （`tests/test_deep_audit_v1201.py`，20 项）。

## 一、会造成用户可见后果的四项

### 1.1 启动时误报「数据目录不可用」（P1）

位置：`gwtool/paths.py` 的 `_ensure_dir`。

成因：判断目录是否可写靠「真写一个临时文件再删掉」，而临时文件名是固定的
`.gwtool_write_test`。这个函数被日志、备份、附件、导出各条路径反复调用，
多线程与多实例（用户把程序双击了两次）都会并发跑它，两个调用方于是互相删除
对方的探针文件。Windows 上删除别人正打开的文件直接报 WinError 32，被异常分支
翻译成「目录不可写」，启动时弹出「数据目录不可用」并拒绝启动，而目录其实完全可写。

实测：8 线程各调用 200 次，误报 1223 次。

修复：探针名带上进程号与随机后缀，删除失败不再算作不可写。

### 1.2 备份恢复时附件静默丢失（P1）

位置：`gwtool/core/attachments.py` 的 `safe_stored_name`，以及新增的
`gwtool/core/naming.py`。

成因：这个函数是外部名字的清洗闸，`backup._restore_attachments` 直接拿它清洗
备份包内的条目名，但漏掉了 Windows 保留设备名（CON、PRN、NUL、COM1 等）。
`open("…/CON.txt", "wb")` 在 Windows 上不报错，却一个字节都没落盘，内容进了设备。
后果是恢复计数照样加一、附件目录里却没有文件；而 `Path.exists()` 又因设备语义
返回真，连「缺失附件清单」都不会报出来。灾难恢复场景下这是最坏的一类故障：
程序说恢复成功，数据其实不在。

修复：把「保留设备名」与「尾点尾空格」两条规则收进 `core/naming.py`，
附件存储与批量汇编共用同一实现（此前是两份，附件这份漏了设备名）。

### 1.3 导出与备份在附件较多时明显卡顿（P1）

位置：`gwtool/paths.py`、`gwtool/core/exporter.py`。

成因：探针要真写盘，在装了实时防护的机器上单次约 45 毫秒，而
`attachments_dir()` 每次调用要走两层探针，实测 89.7 毫秒。导出与备份的附件处理
恰好写在逐条目循环里，等于按附件数量重复付账。

实测：导出 100 个附件从 2.04 秒降到 0.05 秒（APPDATA 目录实测，41 倍）。

修复：同一目录在进程内只探一次，命中缓存时只做一次 stat；目录若在运行期间被删，
自动退回复检重建。导出循环里的目录调用也提到循环外。

### 1.4 正文首行重复（P1）

位置：`gwtool/core/model.py` 的 `DocTree.plain_text`。

成因：解析器在文档没有显式标题时会把首个标题块兼作 title，而 `plain_text`
又无条件把 title 拼在最前，同一行于是在 `content_text` 里出现两次。
`content_text` 是字数统计、查重哈希、全文索引与「导出纯文本」的共同来源，
所以短文档的字数接近翻倍，导出的纯文本首行也会重影。
实测 TXT、MD、HTML 三种导入都重复一次。

修复：首块与标题同文时只保留一份。

## 二、一致性与健壮性四项

### 2.1 麒麟上「跟随系统深浅色」从未生效（P2）

位置：`gwtool/app.py` 的 `run`。

成因：深色判定排在 QApplication 构造之前。非 Windows 平台只能问
`QGuiApplication.styleHints()`，没有应用实例时它返回 `ColorScheme.Unknown`，
于是恒判浅色。实测确认返回值就是 Unknown。

修复：`set_dark` 移到 QApplication 之后、任何窗口创建之前。

### 2.2 移交包可能留下半截文件（P2）

位置：`gwtool/core/exporter.py` 的 `build`。

成因：备份模块早就用「先写临时文件再原子改名」，导出没跟上。打包中断（磁盘满、
目标被占用、进程被杀）会在用户选定的交付路径留下一个看着完整、其实缺文件的包，
而移交意味着责任转移，缺件往往在对方打开时才发现。

修复：改为先写 `.part` 再 `os.replace`，失败时清理临时文件。

### 2.3 督办提醒会静默消失（P2）

位置：`gwtool/core/reminder.py` 的 `enabled`。

成因：读设置失败时返回关闭，与函数自己的文档（默认开启）矛盾。库被短暂占用
这种环境问题，会被表现成「用户关掉了提醒」。

修复：读取失败回落到默认值，与 `config._flag` 同一判断。

### 2.4 启动路径上的数据库句柄泄漏（P2）

位置：`gwtool/app.py` 的 `_follow_system_theme`。

成因：只在成功路径关闭连接，`execute` 抛错时句柄留着。这条路径在启动早期，
遗留句柄会让后面的迁移与恢复在 Windows 上替换不了库文件。

修复：`try/finally` 关闭。

## 三、排查方法与排除的伪阳性

静态层面用扩展规则集扫了全仓，再把「看着像缺陷」的逐个用探针证伪，
以下四类确认不是问题，未作改动：

- 24 处 SQL 拼接告警：全部是列名常量元组加占位符，分组统计另有白名单校验。
- 79 处吞异常的写法：抽查均为「降级不影响主流程」的设计（COM 释放、进度回调、
  纠错层），备份、恢复、导出、导入这些关键路径都有留痕或上报。
- 依赖与配置：15 个第三方导入全部能对上依赖清单，可选推理栈都在函数内惰性导入
  并带降级；打包规格的 UPX 排除项与模块收集都有理由注释。
- 边界输入：9 类畸形文件（空文件、伪装扩展名、坏编码、超大文本、无扩展名）导入
  均返回可读失败原因，不抛异常；22 个大写金额边界样例逐条符合规范。
