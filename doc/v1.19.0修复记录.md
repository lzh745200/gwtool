### 误报治理（真实语料逐条 triage）
开发中在 220 篇真实语料上发现并修掉 5 类误报：
1. 「之所以…**是因为**/**正是因为**/**恰恰因为**」是正确写法 → 加负向先行断言；
2. 「不但…**反而**」是合法对比 → 删除该规则；
3. 「只有**一个**…就是」列举句 → 列举守卫扩展到 v2 整段命中；
4. 「充分彰显…**作为**重要组成部分」被「分…为…组成」跨词误配 → 改为字面「分为…组成」；
5. 「大约/近/至少/超过…左右/以上」跨句误配 → 限定为数字量词紧跟。

## 七、性能优化：写作参考库检索提速（v1.19 同期）

用户反馈"写作参考库加载速度太慢"，要求提升校对/汇编/检索整体性能。
实测定位后发现**慢点不在加载、也不在渲染，而在词典检索的两级全表扫描**。

### 7.1 根因（都有 EXPLAIN 与计时证据）

`dao.search_dictionary` 老实现用三级 LIKE：

| 级别 | SQL | 执行计划 | 12.3 万词条实测 |
|---|---|---|---:|
| ① 精确 | `word = ?` | SEARCH（索引） | 0.04 ms |
| ② 前缀 | `word LIKE 'q%'` | **SCAN**（覆盖索引全扫） | 34 ms |
| ③ 包含 | `word LIKE '%q%'` | **SCAN**（覆盖索引全扫） | 34 ms |

关键在于 `word` 列的索引是 **BINARY 排序规则**，SQLite 只有在该列声明
`COLLATE NOCASE` 时才把 `LIKE '前缀%'` 转成索引范围查询；而 NOCASE 对中文
无效。于是写作参考库的默认检索 `reference.lookup()`
（三源检索 = 文档 + 词典 + 句式）每次都要付两遍整表扫描，实测 **≈85 ms**。

### 7.2 修复

| 级别 | 新实现 | 执行计划 | 效果 |
|---|---|---|---|
| ② 前缀 | `word >= q AND word < q+\uffff` | **SEARCH**（索引范围） | 34 ms → 0.09~0.9 ms |
| ③ 包含 | `instr(word, q) > 0` + 有界探测 | SCAN 但**代价有界** | 无命中时不再重复扫描 |

两处配套：

- **前缀级**：`ORDER BY LENGTH(word)` 会让 SQLite 把**全部**前缀命中建临时
  B 树排序。短前缀（如"安全"）能命中数千条，排序成本反超索引收益
  （0.09 ms → 0.87 ms）；命中数上限 `_DICT_SORT_SCAN_CAP = 2000`，超限时
  改为索引顺序取 top-N + 定向补短词，保证"安全生产"这类短词不被批量相似词条挤掉。
- **包含级**：先做有界探测（`count(*) FROM (… LIMIT CAP+1)`）拿命中规模，
  结论为 0 时**不再扫第二遍**——老实现无论有没有命中都要扫一次表。

### 7.3 效果（真实 4 万纠错对 + 12.3 万词典）

| 指标 | 优化前 | 优化后 | 倍数 |
|---|---:|---:|---|
| `reference.lookup()` 参考库检索 | 84.8 ms | **9.0 ms** | ≈9.4× |
| `search_dictionary('安全')` | 64.9 ms | **24.5 ms** | 2.6× |
| `search_dictionary('安全生产检查')` | 21.8 ms | **8.3 ms** | 2.6× |
| 段落模式检索（含渲染） | 26.2 ms | 约 14 ms | ≈1.9× |

校对与汇编实测本就在合理区间，未改算法：万字 600 处命中 64 ms
（≈6.4 万字/秒，且在后台线程）；生成 200 篇 DOCX 41 ms。

### 7.5 一次被否掉的错误优化（留档防复犯）

曾试图用"查询里每个字都能在某词条的**首字**找到"来前置否决包含级。
那是**错的前提**：`(word)` 索引只能证明某字出现在别的词条词首，
证明不了它出现在目标词条的词中。反例——词典里只有"安全生产"，查"生产"时
"生""产"都不是任何词条首字，前置否决会把合法命中全部误杀。
已由 `test_result_correctness_kept` 守住，并在代码注释中写明勿再犯。

### 7.6 性能契约（防退化）

`tests/test_perf_reference_v119.py` 用**宽松上限**（远高于优化后实测，
慢机器不误报）但足以拦住量级退化：

- 前缀检索（`limit=5`）< 8 ms —— 退回全扫会是 30 ms 以上；
- `EXPLAIN QUERY PLAN` 必须含 `SEARCH` 与 `word>?`，不得是 `SCAN`；
- 包含级 < 60 ms（有界）；
- `reference.lookup()` < 40 ms。
