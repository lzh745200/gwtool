## 六 下载通道备忘（网络受限环境）

`github.com` 的 git 通道与 release 下载**均不通**（`git push` SSL 握手失败；`curl` 下载 `HTTP=000`）。
但 **`api.github.com` 可达**，且资产下载端点会 302 到 `release-assets.githubusercontent.com`（该站可达）：

```bash
# 1) 取 asset id
curl -sL "https://api.github.com/repos/<owner>/<repo>/releases/<release_id>/assets"
# 2) 按 id 下载（必须带 Accept: application/octet-stream）
curl -sL -H "Accept: application/octet-stream" \
     -o <文件名> "https://api.github.com/repos/<owner>/<repo>/releases/assets/<asset_id>"
```

本次两个产物均以此通道下载成功，字节数与 Release 元数据**精确一致**。

### 7.3 ⚠ 已发生的全量误上传事故：`api_commit.py` 的目录过滤漏 `*_new`（最严重）

**这是本轮最危险的一处，且属"同一根因的第二次复发"。**

**现象**：修完 §7.1 的 `.gitignore` 后推送，日志出现：

```
[api] 自动比对：420 个文件需要上传
[api] blob dist_new/gwtool/_internal/PySide6/Qt6Core.dll (10363704 字节) -> 21b1156759
[api] blob dist_new/gwtool/_internal/PySide6/translations/qtbase_zh_CN.qm ...
```

**整个 Qt 运行时（各 `.dll`/`.pyd`/翻译文件）正在被逐个上传。** 已中途 kill 止住。

**为什么 `.gitignore` 修了还不够**：`scripts/api_commit.py --auto` **不读 `.gitignore`**，
它用的是脚本内自己维护的一份 `SKIP_DIRS` 固定名清单（注释写着"与 .gitignore 保持一致"）。
两份清单手工同步 —— 改一处忘一处就是一次全量污染。

**根因与 2026-09-13 那次同源**：那次 `SKIP_DIRS` 漏了 `.venv64`/`.convlib`/`.zcode`/
`.workbuddy`/`packs`，把 3.7 万个环境文件（含 740MB 模型包，超 GitHub 单文件上限）
全量读入比对并上传，"永久卡死且污染仓库"。**这次换了新目录名，原地复现。**

**处置**：
1. **立即终止**（`taskkill //PID` 语法无效，改用 PowerShell `Stop-Process -Force`）。
2. **核对远端未被污染**：`main` 与 tag `v1.6.0` 都仍停在 `ba2fd33ad8`。
   进程死在 blob 上传阶段、**从未走到 `[api] commit`**，故**没有产生任何提交**
   （可能留下未被引用的孤儿 blob，GitHub 会 GC，无害）。
3. **改法**：`SKIP_DIRS` 只留真正固定的名字；新增 `SKIP_DIR_PREFIXES = (".venv","build","dist")`
   与 `is_skipped_dir()`；前缀后须紧跟 `_`/`-`/`.` **或数字**——
   数字分支是必需的，`.venv64` 正是历史事故里点名的真实目录名，只允许符号分隔会让它漏网；
   同时不误伤 `buildings`/`distribution`/`distill`/`buildable`。
4. **护栏**（2 条新用例）：`test_api_commit_skips_variant_build_dirs`（17 组判定，
   含 `.venv64` 与 4 个反例）、`test_api_commit_scan_excludes_local_build_outputs`
   （真跑 `scan_local(ROOT)`，断言待上传清单里无产物）。
5. **实测**：待上传 **420 → 6 个文件**，产物泄漏 0。

**留下的操作习惯**：走 `api_commit.py` 时**先看日志首行的文件数**。正常是几个；
一旦看到 `[api] blob dist_new/...` 之类的产物路径，立刻终止。

### 7.5 已修复：`e2e_check.py` 汇编段内容不唯一（真缺陷，非纯测试问题）

**现象**：`scripts/e2e_check.py` 从 29/29 变成 **27 通过 / 2 失败**：
```
[FAIL] 汇编产物入库+重复识别  新入库 id=-1；重复入库返回 -1
[FAIL] 台账回填 doc_id        台账 id=2，按 doc_id=-1 可反查
```

**根因**：该脚本按自身 docstring 的设计，跑在**真实应用数据目录**上（持久库，
非临时库）。上一轮运行插入的 `汇编成果` 文档留在库里，本轮用**同一段字面量正文**
再插时，`dao.add_document` 按 content hash 正确判定为重复并返回 `-1`
—— **`-1` 是正确行为，是断言的前置条件被历史数据破坏了**。

**为什么第一次没发现**：首次跑时库里还没有那条记录，所以"绿"了。这是典型的
**测试非幂等**：通过与否取决于"之前跑过几次"，而不是代码对不对。

**修法（`scripts/e2e_check.py`）**：正文带上本次运行的唯一标识。
注意唯一性只能取自 `sample_dir.name`（`tempfile.mkdtemp` 的随机后缀）——
**不能取 `out_docx.name`**：那个文件名是固定的 `汇编成果.docx`，两次运行同值
（我第一版就是这么写的，第二次跑立刻复现失败，已纠正）。

**验证**：连续跑 3 次，均 **29 通过 / 0 失败**，且入库 id 依次为 9 → 10 → 11，
证明每次都真的新插入、未再撞 hash。

### 7.6 已补测试：负数 `doc_id` 的守卫边界

排查上面 `-1` 时发现：`dao.add_document` 撞 hash 返回 `-1`，调用方若不判负就会
把 `-1` 写进台账。**这不是假想情形** —— 本次 E2E 失败运行就在真实库里留下了
7 条 `remark='E2E 二次登记'` 的台账记录，其中 2 条 `doc_id=-1`。

复核 `SourceOpenMixin._live_document_id`：

```python
if rec is None or not int(rec.doc_id or 0):   # int(-1 or 0) == -1，真值为 True → 不短路
    return 0
...
if doc is None:                                # ← 真正兜住负数的是这一支
    return 0
```

`not int(-1 or 0)` 是 `False`，**首道判空挡不住负数**；真正拦下的是随后
`dao.get_document(-1)` 查不到行返回 `None`，走 `doc is None` 分支归 0。
即：**该边界靠"查库查不到"兜底，而非设计上的显式判负** —— 属防御性纵深，
行为正确但不够显式。

已新增回归用例 `test_negative_doc_id_is_treated_as_unlinked`
（`tests/test_compile_register.py`），把**最终行为**钉死：`doc_id=-1` 的台账行
「打开原文」必须置灰，且 `_live_document_id` 必须返回 0。
这样即便日后有人删掉 `doc is None` 那一支、或放宽 `get_document` 的容错，
也不会退化成"能点开但打开空白页"。

> 未改动 `_live_document_id` 的实现：当前行为正确，且在无实据表明会出问题时
> 改产品代码属过度修改。仅补测试锁定现状。
