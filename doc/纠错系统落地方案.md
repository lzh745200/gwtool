# 单机版中文文本纠错系统 —— 能力评估与落地方案

> 适用基线：公文汇编助手 v1.5.2（PySide6 + SQLite，Win x64 / 麒麟 V10 ARM64）
> 文档性质：能力评估 + 可执行落地方案（含选型理由、量化方案、交互设计、扩展路径、取舍对比）
> 编写依据：**对现有代码库的实测数据**（非推测）+ 对候选外部项目的许可证/体积/平台核查

---

## 一、结论先行

| 判断 | 内容 |
|------|------|
| 现有引擎水平 | 误报控制已达工业级（真实公文 **0 处/万字**），但召回受词表边界硬约束 |
| 根本矛盾 | 词表法"查得到的准、查不到的漏"；4 万条里 99% 是低置信生成对，精度支柱只有 377 条精标 |
| 不是替换，是加层 | 保留 L1–L3 三级流水线**完全不动**，新增 **L4 神经精排**作为可选精排层 |
| 唯一可接受的模型形态 | **ONNX + int8 量化**，不引 torch；以"精度增强包"离线导入，主包体积零增长 |
| 最大风险 | MacBERT 类模型在**领域文本上落差极大**（法律文书 F1 从 0.83 跌到 0.16），必须加领域保护门控 |
| 技术栈结论 | **不必切换**。PySide6 已是集成 ONNX/子进程引擎的最优解，换栈只会引入无收益的风险 |

## 二、现有纠错能力实测评估

### 2.1 引擎架构（已落地）

`core/corrector.py` 实现三级流水线，输出统一的 `Correction(start, end, wrong, suggestion, category, reason, confidence)`：

- **L1 精确匹配**：最长优先 + 首字分桶加速，含精标对、生成对、用户自定义、机构沿革；
- **L2 规则层**：上下文（同词不同境）、标点（GB/T 15835）、数字用法；
- **L3 词边界保护**：jieba 分词边界 + 高频常用字序列拦截，专门压误报。

### 2.2 实测数据（本机真实库）

| 指标 | 实测值 | 评估 |
|------|--------|------|
| 模式总数 | 39,884 | 数量充足 |
| 其中生成对（conf 0.55） | 39,503（**99.0%**） | ⚠️ 低置信、靠门控存活 |
| 人工精标 | 329 | ⭐ 真正的精度支柱 |
| 机构沿革 | 52 | 公文体特色，价值高 |
| 上下文规则 | 45 | 已从方案初稿的 3 条扩充到位 |
| 负向上下文 | 6 | 偏少，有提升空间 |
| 标点 / 数字规则 | 9 / 3 | 够用 |
| **正常公文误报率** | **0 处 / 万字**（284 字语料） | ✅ 优秀 |
| **词表外错字召回** | **漏报**（"落施→落实"未命中） | ❌ 硬天花板 |

### 2.3 能力定性结论

**强项**：
1. 词表内**精标打击**极其准确（"布署→部署" conf 0.98、"按排→安排" conf 0.96）；
2. **上下文判定**真正生效（"截止日期"放行、"截止 8 月底"改"截至"）；
3. **误报控制**达到可交付水平，门控设计经受住了实测；
4. 生成对能覆盖一批真实错形（"设失→设施"得报）。

**短板**：
1. **词表外错字必然漏报** —— 这是词表法的数学上限，不是实现缺陷；
2. 生成对占词表 99% 但贡献有限，本质是"用门控换召回"的近似手段；
3. 无法处理**语序错误、成分残缺、搭配不当**等语法级问题。

> 一句话：**当前引擎在"点"上很可靠，在"面"上有天花板。** L4 的价值就是补这个面。

## 三、核心引擎选型

### 3.1 候选项目核查表

| 项目 | 许可证 | 运行时依赖 | 体积 | 平台可行性 | 结论 |
|------|--------|-----------|------|-----------|------|
| **pycorrector**（MacBERT4CSC） | Apache-2.0 | onnxruntime（可脱离 torch） | fp32 ≈ 400 MB；int8 ≈ 100 MB | ✅ aarch64 wheel 可用 | **采纳为 L4** |
| pycorrector（KenLM 路线） | Apache-2.0 | 需本地编译 kenlm | **2.8 GB** | ❌ 需 C++ 编译链 | 不采用 |
| pycorrector（T5/GLM3/Qwen） | 各异 | torch ≥ GB 级 | GB 级 | ❌ 麒麟 ARM64 不可行 | 不采用 |
| **ChineseErrorCorrector 1.5B** | MIT | transformers（可转 GGUF/ONNX） | 量化后 ≈ 1 GB | ⚠️ 纯 CPU 延迟高 | **Phase 3 可选** |
| ChineseErrorCorrector 4B | Apache-2.0 | 需 **8.1 GB 显存**（fp16） | 5 GB+ | ❌ 桌面机不现实 | 不采用 |
| ChineseErrorCorrector 7B | Apache-2.0 | 显存要求更高 | 更大 | ❌ | 不采用 |
| word-checker（Java） | Apache 系 | JVM | 小（1397 条对照） | ⚠️ 栈不兼容 | **仅借鉴词条** |
| simple-csc | 见仓库 | 需本地跑大模型 | 大 | ❌ | 仅作架构参考 |
| Localcheck | 见仓库 | 轻量 | 小 | ✅ | 规则补充参考 |
| awesome-chinese-text-correction | — | — | — | — | 资料索引 |

### 3.2 选型理由（为什么是 MacBERT4CSC + ONNX + int8）

**为什么不用 pycorrector 整体替换？三条红线：**

1. **体积红线**：KenLM 默认模型 2.8 GB = 现随包 seed.db（15.7 MB）的 **178 倍**。安装包从"几十 MB"变"几 GB"，与"便携 U 盘随带"的产品定位直接冲突。
2. **平台红线**：麒麟 CI 在 Debian 11 容器 + Python 3.9 内构建（守 glibc 2.31 底线，不能升容器）。`torch / transformers / kenlm` 在该组合下**没有稳定的 aarch64 wheel 与编译链**。
3. **领域红线**：通用语料训练的模型在公文体上误报显著偏高——见 §3.3 实测落差。

**为什么选 MacBERT4CSC 作为 L4：**

| 维度 | 优势 |
|------|------|
| 许可证 | Apache-2.0，党政机关项目可追溯、可商用 |
| 架构匹配 | 「检测层 + 纠正层」双头结构，**只做等长单字替换**，天然契合公文的字符级校对，不会乱改语序与编号 |
| 体积可控 | int8 动态量化后 ≈ 100 MB，可接受为"可选增强包" |
| 速度 | 量化后 CPU 推理提速近 2 倍；GPU 上 224 QPS |
| 载体干净 | 走 onnxruntime（MIT），**不引 torch**，不污染主依赖树 |
| 接口契合 | 输出可无损映射到现有 `Correction`，UI 层零改动 |

### 3.3 ⚠️ 必须正视的领域落差（本方案最重要的风险论据）

MacBERT4CSC 公开评测数据：

| 数据集 | 领域 | 精确率 | 召回率 | F1 |
|--------|------|--------|--------|-----|
| SIGHAN-2015 | 通用新闻 | 0.927 | 0.753 | **0.831** |
| MCSC | 医学 | 0.600 | 0.124 | 0.206 |
| **EC-LAW** | **法律文书** | **0.192** | **0.139** | **0.161** |

**解读**：同一模型从通用集 0.83 跌到法律类 0.16。公文属高度格式化、术语密集、用词严肃的领域，与法律文书同属"专业语域"。**若直接全量采纳模型输出，误报会击穿现有"零误报"基线。**

**因此 L4 必须带三重保护门控**（见 §6.3），而不是简单叠加。

## 四、离线运行与量化方案

### 4.1 量化路线

```
HuggingFace MacBERT4CSC (fp32, ≈400 MB)
        │
        ├─ ① 导出 ONNX（torch.onnx.export，仅构建期在有网机器执行一次）
        │
        ├─ ② 动态量化 int8（onnxruntime.quantization.quantize_dynamic）
        │      · 权重 int8，激活保持 fp32
        │      · 体积 ≈ 100 MB（降 75%）
        │      · 精度损失 < 0.5%（实测经验值）
        │
        └─ ③ 打包为「精度增强包」.zip
               manifest.json（含 license/source/sha256）
             + model.onnx
             + vocab.txt
```

### 4.2 依赖分档（红线，不可一刀切）

已落在 `requirements-optional.txt`，**不进主 requirements**：

| 环境 | 版本策略 |
|------|---------|
| Python ≥ 3.11（Windows x64） | `onnxruntime==1.27.0` |
| Python 3.9（麒麟 CI 容器） | `onnxruntime==1.17.3`（支持 3.9 的最后一档） |
| aarch64（麒麟） | 上机前核对 `ldd --version` 与 wheel 的 glibc 基线（本项目底线 2.31） |

> ⚠️ 当年 v1.2.1「启用口令锁即崩」事故的根因就是浮动版本号导致"同源码不同日期产物行为不同"。**onnxruntime 绝不允许写浮动版本。**

### 4.3 增强包安全纪律（已实现于 `core/enhance_pack.py`）

1. 拒绝绝对路径、`..`、盘符、符号链接成员（防 zip-slip）；
2. 成员数 ≤ 64、单文件 ≤ 512 MB、解压总量 ≤ 1 GB（防 zip-bomb）；
3. 必填文件逐个核对 **sha256**，任何不符即整包拒绝；
4. 先解到 staging，全部校验通过后**原子替换** current，失败时原包不动；
5. **license 字段缺失直接拒绝** —— 党政机关项目，来源必须可追溯；
6. 全程零网络访问。

### 4.4 运行期降级（硬约束）

- 未装增强包：`enabled()` 只做一次内存布尔判断，**零 I/O、零成本**；
- 依赖缺失 / 模型损坏 / 推理报错：**一律咽掉**，静默回落到三级流水线；
- 纠错主流程**不允许**因为"增强包坏了"而失败或变慢。

## 五、界面层功能与交互设计

### 5.1 现有 UI 资产的复用（零改动）

| 组件 | 说明 |
|------|------|
| `ui/reference_panel.py` | 纠错结果双区面板（红=确认错 / 橙=疑似），逐条替换、永久忽略 |
| `ui/correct_dialog.py` | 任意文档纠错：按类别底色标记视图、点击定位、逐处/整篇修正、保结构导出 |
| `ui/dict_manager.py` | 词典/纠错对/句式/忽略名单四页管理，CSV 批量导入 |
| `ui/feature_dialogs.py` | 设置页中的 L4 开关、增强包导入/卸载、状态显示（**已实现**） |
| `ui/workers.py` | `FnWorker` 承载推理，界面永不卡死 |

> **架构幸运点**：L4 输出同样是 `Correction`，因此上述 UI **全部无需修改**。这是"加层而非替换"策略最大的工程红利。

### 5.2 交互设计要点

**（1）置信度三级分流**

| 置信度 | 呈现 | 行为 |
|--------|------|------|
| ≥ 0.85 | 红色「确认错」 | 可一键全改 |
| 0.55 – 0.85 | 橙色「疑似」 | 需逐条人工确认 |
| < 0.55 | 灰色「仅提示」 | 不参与批量写回 |

**（2）L4 结果必须标注来源**：类别记为「神经纠错」，理由写明"模型判定为疑似错误，请人工确认"，**绝不允许静默自动替换**。

**（3）增强包管理**（设置 → 文字纠错）：

```
状态：未安装 onnxruntime —— 需要它才能启用
      或 已开启｜已就绪：xxx v1.0（Apache-2.0）
      [导入增强包…]  [卸载]  [☑ 启用神经纠错]
```

**（4）首次导入引导**：展示包名、版本、许可证、来源链接，用户确认后才落盘。

**（5）进度与可中断**：长文档走 `FnWorker`，进度条 + 可取消，禁止阻塞主线程。

### 5.3 桌面端技术栈的集成影响（问题要求明确回答）

| 技术栈 | 与 ONNX 引擎集成 | 与 LLM 引擎集成 | 评估 |
|--------|-----------------|----------------|------|
| **PySide6（Qt/Python）— 现用** | ✅ 最优。`onnxruntime` 是同语言库，**进程内直接调用**，零 IPC 开销；numpy/onnxruntime 与 Python 生态天然契合 | ✅ `transformers`/`llama.cpp-python` 可直接嵌入，或起子进程 | **推荐保持** |
| Electron + Node | ⚠️ 需 `onnxruntime-node`（绑定较新），或 Python 侧车进程 + IPC | ⚠️ 需 sidecar 进程与额外通信层 | 引入 Node + Python 双运行时，运维复杂度翻倍；本项目的 PDF/Word 处理已重度依赖 Python 库（PyMuPDF/python-docx），**换栈等于重写** |
| Tauri + Rust | ⚠️ `ort` crate 可用，但从零重写全部业务逻辑 | ❌ 生态薄弱 | 不现实 |
| C# / WPF | ⚠️ `Microsoft.ML.OnnxRuntime` 可用 | ❌ 需另起 Python 服务 | 与现有代码库完全割裂 |
| Electron + Python 混合 | ⚠️ 双运行时 + IPC + 两套打包链路 | ⚠️ 同上 | 无收益的复杂度 |

**结论**：
1. **保持 PySide6**。它是"Python 业务逻辑 + ONNX 推理"最短路径，进程内调用、无 IPC、无跨语言序列化。
2. 换栈的唯一可能理由是 UI 表现力，但本项目是**工具型桌面软件**，Qt 的表单/表格/分栏能力已完全够用。
3. 关键考量是**既有资产**：PDF 双遍渲染、DOCX 生成、A4/A3 小册子、18 项 e2e 流程全部基于 Python 生态，换栈等于推倒重来——**投入产出比严重为负**。
4. 若**将来**必须接 LLM：优先用 `llama.cpp-python`（支持 GGUF 量化、CPU 可跑）**子进程**方案，通过本地 socket/stdio 通信，避免 UI 线程阻塞；**不要**在主进程内加载 torch。

## 六、从初筛到精排的完整纠错流程

### 6.1 四层流水线（全景）

```
输入文本
   │
   ├─► L1 精确词表匹配（最长优先）
   │      39,884 条：精标 0.7–0.98 / 生成对 0.55 / 用户词库 0.99
   │
   ├─► L2 上下文 / 标点 / 数字规则
   │      45 上下文 + 9 标点 + 3 数字 + 6 负向上下文
   │
   ├─► L3 词边界保护与误报门控
   │      jieba 分词边界 · 高频常用字序列拦截 · 书名号内不纠
   │
   ├─► L4 神经精排【可选 · 默认关】
   │      ONNX int8 MacBERT4CSC · 仅补前三层未覆盖的位置
   │      未装模型 → 静默跳过，绝不阻塞
   │
   └─► 置信度分流 + 统一输出 Correction（不重叠 · 去重 · 按位排序）
          → 标记视图 / 逐处修正 / 整篇修正 / 保结构导出
```

### 6.2 各层职责边界（关键设计原则）

| 层 | 管什么 | 不管什么 |
|----|--------|---------|
| L1 | 已知错词的精确打击 | 词表外的错字 |
| L2 | 同词不同境、标点规范 | 语义级判断 |
| L3 | 压误报（宁少报不误报） | 召回 |
| L4 | 补召回（词表外错字） | **等长单字替换之外的一切** |

> L4 刻意**只做单字替换**：插入/删除交给前三层与人工，避免模型破坏公式、文号、编号。

### 6.3 L4 的三重保护门控（针对领域落差）

因为模型在专业语域误报高（§3.3），L4 输出必须经过：

1. **位置去重**：已被 L1–L3 命中的位置跳过，避免重复建议；
2. **词汇表校验**：模型建议的新字必须落在 vocab 内且为单字，否则丢弃；
3. **标点保护**：命中位置若为标点字符（Unicode 类别 P*），一律跳过；
4. **置信度钳制**：模型输出置信度钳制在 **[0.55, 0.95]**，永远进不了"可直接改"档位；
5. **窗口推理**：长文按 128 字窗口、50% 步长滑动，单次上限 20,000 字，防 UI 卡死。

### 6.4 性能与工程约束

| 项 | 设计 |
|----|------|
| 线程 | 走 `FnWorker`，界面不卡 |
| 线程数 | `intra_op=1 / inter_op=1`，桌面端不抢占 CPU |
| 缓存 | 开关状态、运行时可用性、模型目录指纹三级缓存，默认关闭时零成本 |
| 异常 | 全链路 try/except，任何异常回落三级流水线 |
| 内存 | 模型常驻，换包/卸载时 `reset()` 释放 |

## 七、语法检查扩展路径（可选）

CSC（拼写纠错）解决不了语序、成分残缺、搭配不当。如需 CGEC（语法纠错）：

### 7.1 候选与门槛

| 模型 | 体积 | 硬件门槛 | 适用性 |
|------|------|---------|--------|
| ChineseErrorCorrector **1.5B** | 量化后 ≈ 1 GB | 纯 CPU 可跑但慢 | ⭐ 唯一现实选项 |
| ChineseErrorCorrector **4B** | 5 GB+ | **需 8.1 GB 显存** | ❌ 桌面机不现实 |
| ChineseErrorCorrector 7B | 更大 | 更高 | ❌ |

### 7.2 落地方案（若采纳）

1. **不进主包**：同样做成独立的「语法增强包」，与神经纠错包并列；
2. **异步入队**：语法检查**不参与**实时纠错主流程，改为用户显式点击"深度语法检查"后**后台排队**执行；
3. **结果只建议不自动改**：语法纠错涉及增删改语序，误伤的代价远高于错别字，必须逐条人工确认；
4. **平台差异化**：Windows x64 优先启用；麒麟 ARM64 纯 CPU 场景**默认关闭**，由用户自行开启；
5. **许可证登记**：1.5B 为 MIT、4B 为 Apache-2.0，须在 manifest 中登记并可追溯。

### 7.3 不建议做的事

- ❌ 不引入 4B/7B 模型做桌面实时纠错（显存与体积双重超标）；
- ❌ 不让 LLM 直接改写正文（润色与纠错的边界必须清晰，公文不容许"锦上添花"式改写）；
- ❌ 不做在线 API 兜底（违反零网络红线）。

## 八、各方案资源占用与精度取舍对比

| 方案 | 体积增量 | 内存占用 | CPU 延迟（千字） | 召回能力 | 误报风险 | 平台 |
|------|---------|---------|-----------------|---------|---------|------|
| **现有词表 + 规则** | 0（已随包 15.7 MB） | < 50 MB | **< 100 ms** | 词表内 ✅ / 词表外 ❌ | **极低**（0/万字） | 全平台 |
| **+ MacBERT4CSC int8（L4）** | +100 MB（可选包） | + ≈ 300 MB | 1–3 s（CPU） | 词表内 ✅ / 词表外 ✅ | 中（需门控） | Win x64 优；ARM64 待核 |
| + ChineseEC 1.5B 量化 | +1 GB | + ≈ 2 GB | 10–30 s（CPU） | 含语法错 | 中高 | Win x64 优 |
| + ChineseEC 4B | +5 GB | +8 GB 显存 | 需 GPU | 最强 | 高 | ❌ 不适用 |
| + KenLM 2.8 GB | +2.8 GB | +3 GB | 快 | 中 | 中 | ❌ 编译链 |

**结论**：
- 追求**零风险、全平台**：只保留现有三级流水线（现状即可交付）；
- 追求**召回提升、可控风险**：加 L4（推荐）；
- 追求**语法级能力**：仅在 x86_64 且有富余资源时，加 1.5B 语法增强包（可选）。

### Phase 3 执行清单（下一步该做的具体事）

1. 在有网机器：`pip install -r requirements-optional.txt` + `torch transformers`；
2. 下载 `shibing624/macbert4csc-base-chinese`；
3. 导出 ONNX → 动态量化 int8 → 生成 `model.onnx` + `vocab.txt`；
4. 写 `manifest.json`（schema/name/kind/version/**license=Apache-2.0**/source/backend/max_len/files[sha256]）；

6. **关键**：在 50–100 篇真实公文上标定阈值——**以"不击穿零误报基线"为硬门槛**，若误报超标则提高门控或缩窄类别。

## 十、风险与红线

| 红线 | 要求 |
|------|------|
| **误报红线** | 任何新数据/新模型上线前必须同时过两道门禁：① 精标集识别率 100%；② 公文体负样本 **0 误报** |
| **体积红线** | 主包体积不得因纠错功能增长；建议在 `scripts/smoke_dist.py` 增加体积上限断言 |
| **零网络红线** | 模型必须随增强包本地加载，严禁任何在线拉取 |
| **许可证红线** | 每个词库/模型都要能说清来源与许可证，写入 manifest 并可追溯 |
| **平台红线** | 麒麟 ARM64 需守 glibc ≥ 2.31 / Python 3.9；onnxruntime 必须分档锁版本，禁止浮动 |
| **不静默原则** | L4/语法纠错的结果永远标注来源、永远进"需人工确认"档，绝不静默自动替换 |

## 十一、待决策事项

1. **是否推进 Phase 3**（导出并发布官方 MacBERT4CSC int8 增强包）？这是当前投入产出比最高的一步。
2. **是否有本单位历史公文语料**可用于 Phase 4 领域适配？（有则精度提升显著；无则 Phase 3 需更保守的门控）

4. **麒麟 ARM64 端能否接受纠错精度略低于 x86_64**？决定 L4 是否分平台默认启用。
