# 麒麟（Kylin）中文输入法不可用：根因分层、修复与验证

> 适用：v1.21 及以后版本，PySide6/Qt6 打包产物，X11 与 Wayland 会话。
> 本文分两部分：**一**是根因分层与判定（现场自证），**二**是本次代码修复与验证步骤。
> 凡标注「待现场核实」的，是我在 Windows 开发机上无法确认的项，请以真机输出为准。

## 一、根因分层：四类，各有判定手段

Qt6 在 Linux 上**不再走 XIM 默认路径**，中文输入必须有输入法框架提供的
`platforminputcontexts` 插件。任何一环断掉，症状都长一样：**窗口能开、英文能打、
切不出中文**。所以先判定断在哪一环，别盲目改环境变量。

| 层 | 断点 | 判定命令（真机执行） | 典型输出 |
|---|---|---|---|
| L1 输入法框架 | 没装 / 没在跑 | `pgrep -a fcitx5 \|\| pgrep -a fcitx \|\| pgrep -a ibus` | 无输出 = 框架没跑 |
| L2 Qt6 前端插件 | 系统没装 Qt6 前端 | `ls /usr/lib/*/qt6/plugins/platforminputcontexts/ 2>/dev/null` | 目录为空或不存在 |
| L3 加载路径 | 打包产物只搜包内插件 | `gwtool.sh --startup-report` 看 `plugin[...]` 行 | 全是 `MISSING` |
| L4 会话类型 | Wayland 下 XIM 无效 | `echo $XDG_SESSION_TYPE` | `wayland` |

四层里 **L2 是最常见的**：麒麟自带的输入法是 fcitx 的 GTK/Qt5 前端，而本程序打包的是
**独立的 Qt 6.11**，系统的 Qt5 插件对它完全无用。系统若没装 Qt6 前端，插件这一环就是空的。

## 二、本次代码修复（三处 + 一处副作用）

### 修复 1：不再盲信 `QT_IM_MODULE`，插件缺失时自动降级

`gwtool/ui/ime.py` `configure()`。

**缺陷**：原实现看到 `QT_IM_MODULE` 有值就照单全收。若该值指向的插件不存在，**Qt 会连
一个输入法插件都不加载**——这比降级到 compose 更糟，等于把输入链路整条切断。而
`gwtool.sh` 会按 `XMODIFIERS` 自动写 `QT_IM_MODULE=fcitx`，于是在"没装 Qt6 前端"的
麒麟上，恰好自动走进这个死路。

**修法**：先用插件清单校验；不可用则记 `invalid_request` 并进入降级链。

### 修复 2：新增 XIM 兜底（不依赖任何 Qt 插件）

降级链现在是四级：

```
用户显式设置且插件存在  → 用它（最佳）
有会话提示且插件存在    → 用它
有提示但插件缺失 + X11  → QT_IM_MODULE=xim（fcitx/ibus 自己提供 XIM 服务，能打中文）
以上都不成立            → compose（只能拉丁字符 + 给出可操作提示）
```

**为什么 XIM 能救急**：XIM 由输入法框架进程提供，Qt 的 xcb 平台插件内置支持，**不需要
任何额外 .so**。代价是候选框位置有时不理想，但"能打中文"优先于"体验完美"。
Wayland 会话下 XIM 不成立，这一点在诊断里明说，并给出 `QT_QPA_PLATFORM=xcb` 的临时方案。

### 修复 3：打包时显式收集 `platforminputcontexts`

`gwtool.spec`。

**缺陷**：PyInstaller 的 PySide6 hook 各版本对该目录的处理不一致——实测 Windows 产物里
只剩 `qtvirtualkeyboardplugin`，Linux 上若同样少了 `libcomposeplatforminputcontextplugin.so`，
降级链的最后一级也落空。

**修法**：只针对这一个子目录做确定性收集（两种 wheel 布局都探：`PySide6/Qt/plugins/…`
与 `PySide6/plugins/…`），失败不阻断打包（运行时还有降级）。

### 配套修复：XIM 兜底成功时不要弹窗

`gwtool/app.py`。

原逻辑是"有 warning 就弹一次框"。加了 XIM 兜底后，输入**明明能用**也会带 warning，
结果每次启动都弹「输入法可能不可用」——用噪音换来的"修复"等于没修。
现改为按 `info["usable"]` 判定：不可用 → 弹窗 + 日志；可用但降级 → 只写日志。

### 诊断增强

`--startup-report` 的输入法段现在会打印：会话类型与 Wayland 标志、`DISPLAY`、
`QT_IM_MODULE` 原值 → 实际选用值、`invalid_request`、每个候选插件的绝对路径或 `MISSING`、
以及一句**结论**（能打中文 / 只能拉丁字符 / 完全不可用）。

## 三、真机验证步骤（4 步，每步都有可判定预期）

在安装目录下执行（`gwtool.sh` 与可执行文件同级）：

### 步骤 1 看程序自报

```bash
./gwtool.sh --startup-report
```

- 预期 A：`QT_IM_MODULE=fcitx -> fcitx`，`plugin[fcitx]: /usr/lib/...so`，结论「当前使用 fcitx 的 Qt6 前端插件」→ **最佳路径**。
- 预期 B：`invalid_request: fcitx（插件缺失，已降级）`，`-> xim`，结论「当前走 XIM 兜底：能输入中文」→ **能打中文，但建议补装前端插件**。
- 预期 C：`-> compose` 或空，结论「打不了中文 / 中文输入不可用」→ 按第四节对症处理。

### 步骤 2 看 Qt 到底加载了哪个插件

```bash
QT_DEBUG_PLUGINS=1 QT_LOGGING_RULES="qt.qpa.input*=true" ./gwtool 2>&1 \
  | grep -iE "platforminputcontext|input method|xim" | head -20
```

- 预期：出现 `loaded library .../platforminputcontexts/libfcitx5platforminputcontextplugin.so`
  或 `Using XIM as input method`。
- 若出现 `Cannot load library ... (undefined symbol)` 或 `uses incompatible Qt library`，
  说明系统插件与包内 Qt 版本不匹配（L4→ABI 问题，属「待现场核实」项），按第五节处理。

### 步骤 3 实测输入（唯一能证明"修好了"的一步）

1. 打开任一可编辑处（文档正文、台账「标题」输入框、搜索框）；
2. 按 `Ctrl+Space`（或 `Super+Space`）切换输入法 → 托盘图标应变为中文输入法图标；
3. 输入 `gongwen` → 应弹出候选框；
4. 选词上屏 → 编辑框出现「公文」。

三步都通过才算修好。只看到图标变化但不出候选框，说明 QPA 拿不到输入法上下文
（回到步骤 2 看插件加载日志）。

### 步骤 4 反向确认（防止"碰巧能用"）

```bash
QT_IM_MODULE=compose ./gwtool
```

- 预期：这一步**故意关掉**中文输入，`Ctrl+Space` 无效、打不出中文。
- 若这一步仍能打中文，说明真正生效的是环境里的别的东西（比如桌面环境的输入法注入），
  那么本次改动对你这台机器不是决定因素——记录下来，别把它当成已验证的修复。

## 四、按判定结果对症处理

### 情形 A：`pgrep fcitx5` 无输出（框架没跑）

```bash
fcitx5 -d            # 或 fcitx -d；并确认 ~/.xprofile 里有导出变量
export XMODIFIERS=@im=fcitx
export GTK_IM_MODULE=fcitx
```

UKUI 桌面可在「控制面板 → 输入法」里启用；Debian 系通用命令是 `im-config -n fcitx5`。
**注意**：这些只影响新开的程序，改完要重开本程序。

### 情形 B：`platforminputcontexts` 目录为空（没装 Qt6 前端）

先搜包名（麒麟各 SP 的仓库命名不完全一致，**以下包名待现场核实**）：

```bash
apt-cache search fcitx5 | grep -i qt      # 常见结果：fcitx5-frontend-qt6 / fcitx5-qt6
sudo apt install fcitx5-frontend-qt6      # 若上面搜到的是别的名字，装搜到的那个
```

装完确认插件落地：

```bash
ls /usr/lib/*/qt6/plugins/platforminputcontexts/
# 期望看到 libfcitx5platforminputcontextplugin.so
```

然后重开程序，回到步骤 1 应看到「预期 A」。

### 情形 C：插件在，但加载报 `incompatible Qt library` / `undefined symbol`

系统插件是针对**系统自带的 Qt6**（麒麟 V10 多为 6.2/6.4）编译的，本程序打包的是
**Qt 6.11**。同主版本理论上向后兼容，但发行版可能用了不同的编译选项。

对策按代价从低到高：

1. **先走 XIM 兜底**（本次已自动）：`QT_IM_MODULE=xim ./gwtool`，能打中文即可用；
2. 若必须用原生插件体验：**临时改成用系统 Qt 运行时**——本程序是 PyInstaller 产物，
   不支持混用系统 Qt，故这条实际不可行，**不建议**；
3. 找与 Qt 6.11 匹配的 fcitx5 qt6 插件（或厂商提供的 Kylin 适配包），
   用 `ldd` 确认它依赖的 `libQt6Core.so.6` 与本程序包内版本一致：

```bash
ldd /usr/lib/*/qt6/plugins/platforminputcontexts/libfcitx5platforminputcontextplugin.so \
  | grep Qt6Core
```

### 情形 D：Wayland 会话

XIM 在 Wayland 下不可用，必须有 Qt6 插件。临时可用 X11 路径：

```bash
QT_QPA_PLATFORM=xcb ./gwtool      # 走 XWayland，之后 XIM 兜底生效
```

长期应装 Qt6 前端插件（情形 B）。纯 Wayland 且无 XWayland 的环境，只能靠插件。

## 六、一段话总结

Qt6 在 Linux 上把输入法从"内建"改成了"插件制"，而麒麟自带的输入法前端是给 Qt5 的。
所以问题不是"程序写错了"，而是**打包的 Qt6 与系统的输入法前端之间少了一座桥**。
本次修复做了三件事：把桥（插件目录）显式打进包、桥不通时不再假装通（校验后降级）、
实在没桥就绕道 XIM 先能打字。剩下的三成，必须到真机上照步骤 1-4 走一遍才算数。
