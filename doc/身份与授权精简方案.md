# 身份、归属与授权的精简方案（单机离线版）

> 结论先行：**单机离线产品不建账号体系**。只保留三层——本机操作员档案、资料库口令锁、
> （可选）离线授权文件。注册、组织架构、角色权限、通行码、有效期心跳，全部不做。
> 本文给出唯一实现路径、逐项取舍理由与关键流程，不提供备选方案。

## 一、先对齐事实：现在到底有什么

| 机制 | 代码位置 | 实际职责 | 判定 |
|---|---|---|---|
| 资料库口令锁 | `gwtool/core/security.py`（PBKDF2，12 万轮）、`app._pass_lock()`、`ui/feature_dialogs.LockDialog` | 启动时挡一次，防止他人随手翻阅本机资料 | **保留**，修一个 fail-open 缺陷 |
| 开关设置 | `settings.lock_enabled`、`settings.lock_hash` | 锁的启用状态与口令摘要 | 保留，键名不变 |
| 注册 / 登录 | 无 | — | **不存在**，不需要新增 |
| 组织架构 | 无 | — | **不存在**，不需要新增 |
| 角色 / 权限 | 无 | — | **不存在**，不需要新增 |
| 机器码 / 通行码 | 无 | — | 仅在**对外发售**时需要，且只做一种形态 |
| 用户表 | 无 | 台账里的拟稿人/核稿人/签发人是**自由文本字段** | 保留文本字段，不建用户表 |

一句话：不是"机制太多要砍"，而是"该补的只有一处，且要按单机的方式补"。

## 二、职责梳理：这些机制各自想解决什么，在单机上成不成立

| 诉求 | 机制名 | 单机场景下这个诉求是否真实存在 | 判定 |
|---|---|---|---|
| 证明"我是谁" | 注册 / 登录 | 不存在。没有服务端、没有多租户，登录只是本地比对一个哈希 | **删除** |
| 区分部门与数据边界 | 组织架构 | 不存在。全库就在这一台机器的一个目录里，没有跨部门数据 | **删除** |
| 控制"谁能看哪部分" | 角色 / 权限矩阵 | 不成立。使用者通常只有一人；即便多人共用一台机器，能开这台电脑的人本来就能直接拷走数据库文件 | **删除** |
| 防止他人随手翻阅 | 口令锁 | 存在，且是唯一真实的安全诉求 | **保留** |
| 留痕：这条台账是谁填的 | 操作员标识 | 存在。台账有拟稿人/核稿人字段，但每次手打 | **新增（轻量）** |
| 软件只授权给买过的人 | 机器码 + 通行码 | 只在对外售卖时存在；内部自用不存在 | **按需保留一种形态** |
| 授权到期自动失效 | 有效期 / 心跳 | 离线内网无法联网校验，心跳必然失效或变成"永久缓存" | **删除** |

**核心判断**：单机离线下，"账号 + 密码 + 角色"提供不了任何真实防护——数据文件在你自己的
磁盘上，绕过界面直接拷 `gwtool.db` 的成本比破解登录低得多。所以安全边界只能是
**防误看**，不能是**防越权**。把"防越权"的那一套搬进单机，换来的是摩擦、忘记密码的
致命风险和一堆没人维护的权限表。

若甲方/招标文件硬性要求"必须有用户管理"，真正要满足的其实是**可追溯**（谁在什么时候
做了什么），而不是**角色矩阵**。用"操作员档案 + 操作日志"满足它，成本不到 RBAC 的十分之一。

## 三、整体结构：三层，两个新模块，一处修缺陷

```
┌─────────────────────────────────────────────────────────────┐
│ L3 授权（可选，仅对外发售时启用）                            │
│    机器码 = 本机指纹 → 授权文件（HMAC 签名，离线验签）        │
│    core/license.py            未启用时整层不参与任何判断      │
├─────────────────────────────────────────────────────────────┤
│ L2 资料库口令锁（保留，全局一把）                            │
│    core/security.py          启动拦一次，只挡界面不加密数据   │
├─────────────────────────────────────────────────────────────┤
│ L1 本机操作员档案（新增，用于留痕，不做鉴权）                 │
│    core/identity.py          当前操作员名 + 可选 4 位 PIN     │
└─────────────────────────────────────────────────────────────┘
         全部落在 settings 表 + 数据目录下的一个授权文件
```

**数据落点**（尽量不加表，避免 schema 迁移）：

| 键 / 文件 | 内容 | 说明 |
|---|---|---|
| `settings.operator_name` | 当前操作员姓名 | 台账拟稿人默认值、日志署名 |
| `settings.operator_pin_hash` | 可选，PBKDF2 摘要 | 仅用于"切换操作员"时的一句确认 |
| `settings.lock_enabled` / `lock_hash` | 沿用现有 | 不改键名，老库直接兼容 |
| `<数据目录>/license.json` | 机器码 + 授权码 + 签发信息 | 明文 JSON，只有授权码带签名 |

## 四、逐项取舍与理由

### 4.1 L1 操作员档案：只留一个名字，不做账号

- **保留**：一个"当前操作员"名字，写入 `settings`；台账新增时自动填入拟稿人；操作日志署名。
- **不做**：注册、密码、头像、多用户表、登录页、会话。
- **可选 PIN 的定位**：4 位数字，只在"切换操作员"时问一次，用来防"张三顺手用李四的名义
  记了一条"。**它不是密码**，不参与任何鉴权，忘记可清空。
- **理由**：单机上"身份"的唯一价值是可追溯。做成账号体系后，用户忘记密码就进不去自己
  的资料库——收益为零，代价是数据被锁死。

### 4.2 L2 口令锁：保留，但必须修掉现在的 fail-open

现状缺陷：`app._pass_lock()` 里 `if not has_password(): return True`。当 `lock_enabled=1`
而 `lock_hash` 为空或损坏（手工改库、异常断电写入中断）时，**锁静默失效直接放行**。
用户以为开着锁，实际谁都能进。

修法（不引新依赖）：
1. 口令锁**启用但摘要无效**时，判为"锁定状态异常"，弹一次说明窗口，并给出两个明确出口：
   「重设口令」或「关闭口令锁」。**不给"直接进入"这个出口。**
2. 口令校验失败累计 5 次后，本次启动只允许"退出"，不再给输入框（防呆，不防暴力——单机
   暴力破解成本本来就低，这里是防手滑）。
3. 明确写进界面文案：**口令只挡界面，不加密数据**。用户换机/重装时只要拿到数据目录就能
   打开，救援路径是"备份包 + 重设口令"，不是"找回密码"。

注：启用/解除口令锁时的写入顺序（先写摘要再写开关、先清摘要再关开关）现状已经正确，
不需要改；上面第 1 条要补的是**读取侧**的判断。

### 4.3 L3 授权：只在对外发售时启用，且只做一种形态

- **机器码**：取三项本机指纹，归一化后取 SHA256 前 16 位十六进制，可读形式分 4 组
  （如 `A1B2-C3D4-E5F6-7890`）。三源与匹配规则：
  - Windows：CPU 序列号（`Win32_Processor.ProcessorId`）、主板序列号（`Win32_BaseBoard.SerialNumber`）、
    系统盘卷序列号；
  - 麒麟/ARM64：`/etc/machine-id`、设备树序列号（`/proc/device-tree/serial-number`）、根分区 UUID。
  - **三选二匹配即通过**：换硬盘、重装系统都不会让授权失效；换整机才失效，这才符合真实售后场景。
- **授权文件**：`license.json`，字段为 `machine`、`issued_to`、`edition`、`issued_at`、`sig`。
  `sig = HMAC-SHA256(内置密钥, machine|issued_to|edition|issued_at)`，用标准库 `hmac`，
  **零新增依赖**（引入 `cryptography`/Ed25519 会让 ARM64 打包与麒麟适配成本明显上升）。
- **明确它的强度定位**：这是"防君子"级，不是密码学级——有心逆向 exe 的人能提取密钥伪造。
  桌面单机产品的授权本来就是这个定位；真要强授权，必须上服务端在线校验，而本项目是
  **完全离线、零网络**，所以不做。
- **不做**：在线激活、通行码（第二把钥匙）、有效期心跳、试用期倒计时、按功能模块分授权档。

### 4.4 为什么通行码要砍掉

通行码（一机一码，输入才可用）本质是"在授权文件之外再插一道人工环节"。它解决的问题是
"防止复制授权文件到另一台机器"，而这个问题机器码绑定已经解决了。多这一层只会带来：
用户把码弄丢 → 软件打不开 → 你必须人工补发 → 售后成本无上限。**留机器码，删通行码。**

## 五、关键流程

### 流程 1 首次使用（不设锁、不设操作员）
1. 启动 → 直接进主界面（零门槛，符合"打开就能用"的工具定位）；
2. 首次写台账时，拟稿人栏为空 → 提示一次"填写你的姓名，以后自动带入"；
3. 写入 `settings.operator_name`，之后不再打扰。

### 流程 2 启用口令锁
1. 设置 → 安全 → 启用口令锁 → 输入两次口令（≥4 位，沿用现状口径，不抬高门槛，
   避免老用户被强制改口令）；
2. 写入顺序：**先写 `lock_hash`、再写 `lock_enabled=1`**。现状 `_set_pw` 已经是这个顺序，
   保持不动 —— 顺序反了会出现"已启用但无口令"的空窗，正好触发下面那个 fail-open；
3. 下次启动弹一次解锁框。

### 流程 3 日常启动（已启用锁）
1. 启动 → 解锁框 → 校验 PBKDF2 → 进入；
2. 连续 5 次失败 → 只允许退出；
3. 摘要无效（数据损坏）→ 说明窗口 + 「重设口令」/「关闭锁」两个出口。

### 流程 4 换人 / 多人共用一台机器
1. 设置 → 当前操作员 → 选择或新增姓名；
2. 若该姓名设过 PIN，问一次 PIN 再切换；
3. 切换只影响后续台账的默认值和日志署名，**不影响能看什么**（单机没有数据边界）。

### 流程 5 对外授权（仅发售版）
1. 用户装好后首次启动 → 未授权状态，界面顶部一条横幅 + 「复制机器码」按钮；
2. 用户把机器码发给你 → 你用签发脚本生成 `license.json` 回传；
3. 用户在「导入授权」里选择该文件 → 校验机器码（三选二）与签名 → 写入数据目录 → 横幅消失；
4. 换机：新机器码 → 重新签发一次（建议同一购买方允许 2 次，写进售后政策）。

## 六、落地清单与工作量（单人口径）

| 项 | 改动 | 工作量 |
|---|---|---|
| L2 修 fail-open + 重设出口 + 失败计数 | `app._pass_lock`、`core/security.py`、`LockDialog` | 0.5-1 人天 |
| L1 操作员档案（设置项 + 台账默认值 + 切换对话框 + 日志署名） | 新增 `core/identity.py`；改 `ui/registry_dialog.py`、设置页 | 1-1.5 人天 |
| L3 授权（机器码采集 + 验签 + 导入界面 + 签发脚本） | 新增 `core/license.py`、`scripts/issue_license.py` | 1.5-2.5 人天，含 ARM64 取指纹的降级路径 |
| 测试 | 每条流程 3 条可判定用例：正常 / 边界 / 异常 | 0.5-1 人天 |

合计 **3.5-6 人天**，其中 L3 只在需要对外发售时做；内部自用只做 L1+L2，**1.5-2.5 人天**。

**迁移注意**：
- 不新增数据库表，只加 `settings` 键，老库直接可用（无 schema 迁移风险）；
- `lock_enabled` / `lock_hash` 键名保持不变，已启用口令锁的用户升级后行为一致；
- 修 fail-open 后，极少数"锁已启用但摘要为空"的老库会首次遇到"锁定异常"提示，属预期。

## 七、明确不做（附理由）

| 不做 | 理由 |
|---|---|
| 注册 / 登录 / 会话 | 无服务端；本地比对没有任何鉴权意义，只增加忘记密码的风险 |
| 组织架构 / 部门树 | 单机一份数据，没有跨部门数据边界可划 |
| 角色 + 权限矩阵 | 使用者是一个人或一台共用机，权限只能限制自己；真要隔离，隔离的是"人"不是"角色" |
| 通行码 | 机器码绑定已解决复制问题，多一把钥匙只增加售后成本 |
| 授权有效期 + 心跳 | 离线内网无法联网校验，心跳必然退化成"永久缓存"，等于没做 |
| 用户表 + 外键 | 台账的拟稿人是自由文本，够用；建表会把"记录一个名字"变成"先建账号" |

## 八、一句话总结

单机版的"身份与授权"，正确形态是：**一个名字用于留痕，一把锁用于防误看，一份签名文件
用于防扩散**。其余机制解决的问题在这台机器上不存在，做进去只会变成售后负担。
