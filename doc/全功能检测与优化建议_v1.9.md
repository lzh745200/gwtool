## 一、结论先行

1. **系统整体是健康的**：五份审计合计 **P0 = 2、P1 = 35、P2 = 50**（P1 分节合计 34 条 + 汇总新增 1 条：P1-35 段落索引体积）；其中唯一会造成**用户数据被改坏**的 P0 只有 1 个（任意文档纠错的过期结果），另一个 P0 是**评测工具口径**问题（不是产品故障）。没有发现"启动即崩、数据丢失、静默丢正文"级别的缺陷。
2. **最该先修的不是新功能，而是"产物保真"和"度量口径"**：
   - 排版侧三处硬伤（docx 行距 32.4pt vs 28pt、内置 PDF 渲染器忽略行距、WPS 下目录域不更新）直接决定**汇编件能不能交付**；
   - 评测侧 `eval_corrector.py` 默认就是红灯（E4 FAIL、exit 1），且 E3/E5/E6 在 224 字小样上"空过"——**现在的数字不能当门禁**。
3. **写作与纠错的能力边界已经清楚**：纠错的精度在真实语料上可用（低置信误报 0.52 处/万字），但"标点类可自动替换"会改坏代码/URL；写作侧最大问题不是能力缺失，而是**对规范公文的误报**（一是/二是误判跳号、法定文种必报"更像经验总结"、对齐序号假阳性）。
4. **台账/资料库有 6 处业务数据正确性问题**：归档档号重号、收文非法日期入库且督办静默跳过、分类树计数漏未分类、检索截断文案错误、历史版本跨文档串档、发文字号无唯一约束——这些都**不需要新功能，只需要修对**。
5. **明确不建议做**：大模型生成/改写正文、换 Web 架构、云同步、引入 pycorrector/torch 全套、列表分页（实测无必要）。理由见 §八。

**如果只做 10 件事（按投入产出排序）**：

## 五、问题总清单

> 编号规则：`P0-*`/`P1-*` 全局唯一；每条给"证据 / 影响 / 改法 / 成本 / 复核状态"。P2 只列主题（细节见五份分节报告）。

### 5.1 P0（必须优先，数据/度量可信度）

**P0-1 任意文档纠错：扫描期间改输入框 → 过期偏移被应用，把无关文字改成建议词**
- 证据：**[实测·主控]** 复现：扫描结果为 `布署@2..4`；用户把文本改为「这是新文件内容。」后点「应用此修正」→ 变成「这是部署件内容。」。源码：`ui/correct_dialog.py` 的 `_on_checked` 不校验快照、`_set_busy` 不禁用 `input_box`。
- 影响：**静默改坏正文**；导出修正稿会把错文本落盘。
- 改法：给每次扫描绑定输入指纹（`hash(input_box.text())` 或块版本号）；`_on_checked` 指纹不符即丢弃并提示"文本已变更，已重新扫描"；应用前再校验块哈希；扫描期间输入框置只读（或允许输入但标记结果过期）。
- 成本：3 h。验收：新增回归用例（模拟编辑→回调→列表为空/提示过期→不产生修改），以及"扫描中打字"的 UI 冒烟。
- 复核状态：**已复现（主控）**。

**P0-2 评测工具默认即红灯，且小语料指标"空过" → 现在的评测数字不能当门禁**
- 证据：**[实测·主控]** `python scripts/eval_corrector.py` → `通过 5/6，未达标 E4（1/23 = 4.3%），exit 1`；E3/E5 的负样本仅 224 汉字（1 处命中即 44.6 处/万字，0 命中时 95% 置信上界≈134 处/万字，统计上无意义）；E6 在未安装增强包时也判 PASS（增强层根本没启用）。
- 影响：`eval` 无法进 CI；"精标 100%""0 处/万字"这类结论不可复核（本次审计也观察到用仓库技术文档当负样本会得到 135 处/万字，属口径错误而非产品退化）。
- 改法（脚本级，不动引擎）：① 增加 `--profile base|l4|l5|all`：未装包/未启用的项输出 **SKIP** 而非 FAIL；② 无 `--corpus` 时 E3/E5/E6 标"示意·不参与门禁"；③ CI 增加 `--profile base` 步骤（只断言 E1/E2/E3/E5）；④ JSON 里写入 profile、语料指纹、样本量。
- 成本：5 h。验收：CI 新增步骤绿灯；有增强包机器跑 `all` 时 E4/E6 真实生效；`--corpus` 缺省时输出明确的"示意"标记。
- 复核状态：**已复现（主控）**。注：这不是"三道门禁"（pytest/ruff/e2e）失败——那三道本身全绿；是评测工具自身的口径问题。
