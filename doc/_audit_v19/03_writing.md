> 审计对象：<仓库根>「公文汇编助手」v1.8.0　写作辅助功能域
> 审计角色：只读审计员（**未修改任何源码**）
> 环境：`.venv\Scripts\python.exe`（CPython 3.13.14 / PySide6 6.11.2 / Windows x64）
> 语料：仓库 `doc/*.md` 22 篇（37.1 万字符，真实长文）＋本篇自撰规范公文样张 8 篇 ＋ 逐项检查正/反例 16 组

## 结论先行（六条）

1. **红线守住了**：写作侧 8 个 core 模块 **零 PySide6 依赖、零写回接口、零网络、零模型**；`WritingHintsDialog` 的构造签名里没有 `insert_cb`（与 `StyleCheckDialog` 有 `insert_cb` 形成对照），"只给建议、绝不写回正文"是**结构性**的，不是靠自觉（§2.8）。
2. **最大问题是"合法公文被误报"**，不是漏报：规范公文上 16 项检查正例全中（16/16），但 2 类高频误报实测存在——「一是二是」被逐段误判为**跳号**（经验材料样张 3 条、经验总结样张 2 条）、法定文种（通知/请示/报告）**必然**被提示"本文更像「经验总结」"（§3 P1-1/P1-5）。
3. **段落对齐的"序号重复"是假阳性**：把参考段落原样贴回草稿（**逐字相同**）做对齐，仍报 3 条"序号重复"；根因是 `_ordinal_issues` 的 `seen` 不随一级标题复位（§3 P1-2）。
4. **骨架槽位抽取的"单位名"一类质量偏低**：11 句人工标注上槽位**类型**召回 11/12、**实体级精确率 9/14**，但单位名一类**几乎不可用**——4 个含单位名的句子 org 槽位 **0/4 精确**（"市教育局"抽成"教育局"、"市生态环境局"漏抽、"市住房和城乡建设局"截成"城乡建设局"、整句 36 字符被吞成一个 `{org}`），另有 2 句把"各单位"抽成单位名（§3 P1-3）。
5. **性能只有一处真热点**：100 页（6.2 万字）写作提示总耗时 **272.2 ms**，其中 `_element_hints` 一项占 **196.7 ms（72%）**，且跑在 UI 线程的对话框构造函数里（§3 P1-4）；其余路径都在毫秒级（段落检索 0.2–1.7 ms、风格校验 15 ms、文内一致性 32 ms）。
6. **报告数字要收口**：README/v1.8 称"16 项检查"，`hints()` 实际执行 **15 个检查函数**；`style_profile.report_lines` 的"十项契约"实测**恒定出现 7 项**（其余按命中条件出现，最多 9 项）（§3 P2-1）。

### 2.4 段落参考（paragraph_ref.py）

#### 索引构建（"71 篇样例库"替代方案）

> 仓库 `doc/` 只有 22 篇工程文档，**不存在 71 篇样例库**。用可复跑规则构造：22 篇按 `## ` 切段后取前 71 段独立成篇（56,090 字符）；同时给出"22 篇全文 371,221 字符"这个真实规模点。

| 场景 | 文档 | 段落 | 耗时 |
|---|---|---|---|
| 71 段片段库 全量重建（`rebuild_paragraphs(incremental=False)`） | 71 | 875 | **119.6 ms** |
| 22 篇全文 全量重建 | 93（71 段片段 + 22 篇全文） | 7,848 | **982.3 ms** |
| 增量重建（内容未变） | 93 | 7,848 | **3.4 ms**，`rescanned=0` |
| 导入路径（add_document 内同步建索引，71 篇） | 71 | 875 | 1,273.6 ms |
| 单篇派生 `derive_blocks` | 22 | 428 | 1.8 ms（**0.08 ms/篇**） |

外推：371k 字符≈982 ms ⇒ 约 **2.6 ms/千字**；典型 71 篇 × 3,000 字（≈21 万字）约 **0.55 s**，落在后台回填（`main_window.py:746+`）里可接受。

## 3. 缺陷与风险

> 分级口径：**P0** = 数据损坏/崩溃/写回正文；**P1** = 规范公文高频误报、明显格式错误、UI 卡顿；**P2** = 口径/体验/规模化风险。

### P1（建议 v1.9 修复）

#### P1-1 「一是/二是」逐段被判"跳号"（写作提示）

- **现象**：公文最常见的段内枚举写法（每个"一是"独立成段）被报 `层次序号不规范：跳号`，且耗光 3 条上限，把真正的序号问题挤掉。
- **证据**：经验材料样张（1256 字）出 3 条、经验总结样张（1236 字）出 2 条；最小复现：
  ```python
  typical = "一、主要做法\n\n一是建强平台。\n\n二是织密网格。\n\n三是打通数据。\n\n四是健全机制。\n"
  [h.title for h in writing_hints.hints(typical) if "跳号" in h.title]
  # ['层次序号不规范：跳号', '层次序号不规范：跳号', '层次序号不规范：跳号']
  # 文案：「第 3 行的「二是」：前一处为「无」，按顺序应为「一是」」
  ```
- **根因**：`writing_hints.py:488-493` 对 level==4 在**每一行**都复位 `next_val[4]=1`；`_:504-511` 于是把第 2 行起的"二是/三是"判为 `value > expected` → 跳号。注释意图是"下一段可重新从一是起"，但实现成了"每行都重新起"。
- **关键区分**：同一行内写完"一是…二是…三是…"（lead 复核脚本 B 的写法）**不报**；每个"一是"各自成段（Word 里一个段落一个"一是"，公文实际排版）**必报**。复核时请用下面这种排版。
- **影响面**：调研报告（语料中位 9 次一是二是）、经验材料（6 次）、经验总结（5 次）——**最主流的三种文体必踩**；每条都是 info 级，但 3 条上限会被假阳性吃满。
- **复现**：
  ```python
  from gwtool.core import writing_hints as wh
  exp = '一、主要做法\n\n一是加强组织领导。\n\n二是健全工作机制。\n\n三是强化督导考核。\n'
  [h.title for h in wh.hints(exp, '') if '序号' in h.title]
  # ['层次序号不规范：跳号', '层次序号不规范：跳号']
  ```

#### P1-2 内容对齐把跨章节的（一）（二）（三）判"序号重复"

- **现象**：参考段落与草稿**逐字相同**时仍报 3 条 `序号重复`；改措辞后同样 3 条。
- **证据**：规范通知（三、工作要求下有（一）（二）（三），二、工作安排下也有（一）（二）（三））→ `align_identical: total 19, matched 16, level_mismatch 3`。
- **根因**：`paragraph_ref.py:628-677` 的 `seen: set[int]` 按**全文**累计，遇到新的一级标题不复位；`expect = len(seen)`（`:669`）因此永远不归零。
- **最小复现（注意签名是 `align_to_draft(draft_text, refs)`，不是 `(refs, draft)`）**：
  ```python
  import sys; sys.path.insert(0, '.')
  from gwtool.core import paragraph_ref as pr
  para = ('一、总体要求\n（一）提高认识。\n（二）明确目标。\n'
          '二、重点任务\n（一）抓好落实。\n（二）强化保障。\n')
  refs = pr.split_draft(para)            # 参考段落
  for a in pr.align_to_draft(para, refs):
      print(a.relation, a.hint)
  # matched ×6，然后：
  # level_mismatch 第 5 段序号「1」重复（同一层级内）
  # level_mismatch 第 6 段序号「2」重复（同一层级内）
  ```
- **影响面**："内容对齐"是 v7 新增卖点；凡是分层标题的公文（几乎全部）都会出现假差异，用户会对整个差异列表失去信任。
- **复现**：`pr._ordinal_issues(pr.split_draft(<规范通知全文>))` → 3 条。

#### P1-3 单位名槽位过度吞并 / 截断 / 漏抽（骨架生成 + 要素提示）

- **现象**：
  - 过度吞并：36 字符整句被抽成 `{org}`（含"，"、"。"）；
  - 截断："市住房和城乡建设局"→"城乡建设局"，"市教育局"→"教育局"；
  - 漏抽："市生态环境局"完全抽不到（→ 骨架里没有单位槽位）。
- **证据**：槽位**类型**召回 11/12、**实体级精确率 9/14**；单位名一类 4 个含 org 的句子里 **0/4 精确**；`skeleton_no_invention` 里出现 `org3 = "校外培训机构，重点检查校舍建筑、消防设施、食品卫…"`、`org4 = "（二）复查阶段。各区县教育局"`。
- **根因**（`paragraph_ref.py:731-759`）：
  1. `_ORG_STOP`（`:710-711`）只收动词/虚词，**不含逗号、句号、括号**，"。"不是停用字 → 左合并会跨句读；
  2. `if beg - ps > _ORG_MAX_PREFIX`（`:754-755`）比较的是**上一个 token 的长度**，不是累计前缀长度 → 逐 token 逐个 5 字以内就能无限向左吃；
  3. `len(word) < 2`（`:740`）直接丢弃单字 token，"市生态环境局"被 jieba 切成 `生态环境`+`局` 时整体失效；
  4. `_ORG_STOP` 含"和"（`:710`），"住房和城乡建设局"在"和"处断开。
- **影响面**：①"从参考段落生成草稿"的槽位示例错 → 用户填出来的稿子是错的（模块自己把"误抽"列为最坏后果，见 `:686-689` 注释）；②写作提示的"未识别到单位名称"据此判断，抽到"各单位"就算"识别到了"。
- **复现**：`pr._find_org_spans("排查范围包括校外培训机构，重点检查校舍建筑、消防设施等方面。各区县教育局要结合实际制定方案。")` → 1 条 span，长度 36。

#### P1-4 写作提示在 UI 线程卡 0.3 s，`_element_hints` 占 72%

- **现象**：100 页（62,849 字符）稿子打开「写作提示与灵感」对话框即卡顿。
- **证据**：`hints()` 总 **272.2 ms**，分项 `_element_hints` **196.7 ms**、`_doc_consistency_hints` 31.4、`_style_hints` 14.1、`_repeat_hints` 14.9；对话框构造函数里**同步**调 `run_hints()`＋`run_ideas()`（`feature_dialogs.py:2269-2270`）。
- **根因**：`_element_hints`（`writing_hints.py:245-264`）对**全文**跑 `paragraph_ref.extract_slots` → 全文 jieba `tokenize`（`db/tokenize.py:115-123`，`jieba.tokenize` 逐词生成 span）＋ 5 条正则；而它只需要回答"有没有单位名/日期/时限"。
- **影响面**：长文（>50 页）用户每次打开对话框都卡；麒麟 ARM64 上预计 ×2–4。
- **复现**：`wh.hints(62k 字符, "工作意见")` 计时。

#### P1-5 法定文种（12 种）必然被提示"本文更像「X」"

- **现象**：声明文种为"通知"的规范通知，被提示 `本文更像「经验总结」`。
- **证据**：`hints(NOTICE_GOOD, "通知")` 第 2 条即此；`detect_kind(NOTICE_GOOD)` top1=经验总结；`detect_kind` 对"请示"同样返回经验总结。
- **根因**：`detect_kind` 只在 7 个**写作文体**里排序（`style_data.STYLES`），而法定公文**刻意没有参数行**（`style_data.NO_PARAM:70-73`）；`_style_hints:297-301` 却拿用户选定的 kind（12 法定文种之一）直接比对，**对任何法定文种恒不相等**。
- **影响面**：所有以 12 文种起稿的公文（产品的核心场景）都多一条无效提示，且该提示**看起来像"你选错了文种"**，会诱导用户改错。
- **复现**：`wh.hints(<任一通知稿>, "通知")`。

#### P1-6 完成时限只认"N个工作日内"，日期写法被判缺失

- **现象**：正文写"于2026年9月20日前完成自查"（公文最标准的时限写法）→ 提示 `未识别到完成时限`；写"3个工作日内"→ 不提示。
- **证据**：`deadline_detection`：日期式样张出 1 条，N 个工作日式样张 0 条。
- **根因**：`_RE_DEADLINE = r"[0-9一二三四五六七八九十两]+\s*个工作日内"`（`writing_hints.py:692`），且只在 kind ∈ {通知,意见,指示,决定,方案} 时检查（`:261-263`）。
- **影响面**：通知/意见/指示类的正文几乎都用日期式时限 → 这类提示**在规范稿上几乎必假**。

#### P1-7 新建公文：主送机关出现双冒号

- **现象**：用户在"主送机关"框按提示输入"各区县教育局："（带冒号，因为提示就是"以冒号收尾"），生成稿出现 `各区县教育局：：`。
- **证据**：`double_colon → ['各区县教育局：：']`。
- **根因**：模板 `recipient = "{recipients}："`（`skeletons.py:85/94/105…`）＋ 对话框原样传值（`feature_dialogs.py:110-114`）不做去尾冒号。
- **影响面**：生成稿的**格式错误**直接进编辑器（用户往往不会注意）；而本产品主打"格式合规"。
- **复现**：见 §2.5 三行片段。

## 5. 不建议做（及理由）

| 方案 | 为什么不做 |
|---|---|
| **用大模型生成公文正文**（"输入主题→出全文"） | ①与红线正面冲突：主包不带模型、不新增运行时依赖；现有 `packs/` 里 43 MB + 30 MB 是**纠错**增强包（且不随主包分发），生成要的是另一套权重，体积/ARM 推理成本都不可控。②与模块铁律 G1 冲突（`style_data.GENERATE_RULES:409-415`：无法核实的内容一律【待补】，绝不编造）；生成式输出**无法逐句溯源**，公文一旦编造数据/引用，责任在用户。③质量不可验收：本域已有可量化验收（`doc/公文风格量化指标与验收标准.md`），生成式输出没有对应的稳定口径。 |
| **让写作提示"一键应用改写"** | `writing_hints` 的结论是**描述性句子**（"第 12 段重复用语：负责同志"），没有可替换文本；`consistency` 更是**故意**不产出替换文本（`consistency.py:11-16` 记录了 ADVISORY 类被误写回的旧坑）。加"一键应用"就得给每条提示编造替换文本，等于让辅助写回正文——直接越红线。 |
| **把提示当合格线：自动把稿子改到参数区间内** | 模块头已明确反对（`style_profile.py:10-13`）：语料里写得最好的几篇**没有一篇全项落在常见区间内**；"改均匀"会把好稿改成平庸稿。只应保留"硬冲突判错 + 其余对照"。 |
| **用词向量/语义模型做段落对齐** | 需要新依赖（体积/许可/ARM 推理三重风险），且破坏"可解释、确定性"这一当前卖点（`paragraph_ref.py:11-17`）。当前的角色级对齐 + 序号连续性已能覆盖"缺章/多章/序号乱"这类真实需求。 |
| **用 LLM 做槽位抽取** | 误抽代价最高（把参考原文的具体事项悄悄换成空槽，用户填完才发现），且不可解释；当前 6 类确定性规则的问题（P1-3）用纯规则就能修到可用。 |
| **给 12 个法定文种补量化参数行** | 法定公文结构由制度锁定（`style_data.py:68-73` 已说明），参数化会制造"看起来科学"的伪指标；且需要重新统计语料才有一手数据，当前 229 篇语料里法定文种占比不足。 |
| **把一致性结论并入纠错流水线** | 会污染"全部应用/批量写回"（正是 `ADVISORY_CATEGORIES` 踩过的坑，`consistency.py:11-12`）。保持"只出现在写作提示侧"是正确设计。 |
| **引入前端图表/雷达图展示 14 项指标** | 现有"位置条 + 数值"已足够；加图表要引入绘制代码与依赖，收益低（且 PIL/Qt 绘图会拉大 UI 复杂度）。 |
